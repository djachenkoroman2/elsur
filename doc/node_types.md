# Типы узлов, применимые к методике расчёта живучести

Документ описывает, какие элементы компьютерной сети (узлы) можно оценивать
при помощи реализованной в приложении `survivability` методики, на каких
условиях, и как сводить к модели узлы со сложной внутренней структурой.

## 1. Условия применимости методики

Методика (марковская модель «отказ–восстановление», см.
[user-guide.md](user-guide.md) и [formulas.tex](formulas.tex))
применима к элементу $e_i$, если выполняются условия:

1. **Два состояния.** Узел в каждый момент времени либо работоспособен
   ($x_i = 1$), либо находится в отказе/поражён ($x_i = 0$). Промежуточные
   состояния («работает с деградацией») напрямую не моделируются.
2. **Пуассоновские потоки ущерба.** Собственные отказы и каждое деструктивное
   воздействие (атака, разрыв канала, отказ питания) проявляются как события
   с постоянной интенсивностью $\lambda$, а вероятность того, что очередная
   реализация воздействия поражает узел ($p_{ij}$), не зависит от истории.
3. **Экспоненциальное восстановление.** Время восстановления описывается одной
   интенсивностью $\mu$ (отсутствие восстановления — частный случай $\mu = 0$).
4. **Агрегирование.** Узел рассматривается как «чёрный ящик»: внутренняя
   структура (компоненты, резервирование) свёрнута в эквивалентные
   $\lambda_i^{(0)}$, $\mu$ и $p_{ij}$.

Если условия выполнены, результатом расчёта является живучесть узла
$Q_i = P(x_i(T) = 1)$ за период $T$.

## 2. Узлы, которые можно рассчитывать

### 2.1. Вычислительные узлы

| Тип узла | Примеры | Воздействия (типовые $d_j$) | Пример JSON |
|----------|---------|------------------------------|-------------|
| Серверы приложений и БД | сервер маршрутизации, СУБД, веб-сервер | DDoS, внедрение вредоносного кода, эксплуатация уязвимостей ПО | [examples/example1_basic.json](../examples/example1_basic.json) |
| Центры обработки данных / кластеры | ЦОД, ЦОИ, кластер ЦМ БД | комплекс внешних (Н1–Н4) и внутренних нарушителей | [examples/example3_many_impacts.json](../examples/example3_many_impacts.json) |
| АРМ пользователей | рабочая станция оператора | НСД, фишинг, заражение вредоносным ПО | — |
| Встраиваемые и специализированные ЭВМ | контроллеры, шлюзы, бортовые вычислители | отказ питания, РЭП, физическое воздействие | — |

### 2.2. Сетевые узлы

| Тип узла | Примеры | Воздействия | Примечание |
|----------|---------|--------------|------------|
| Маршрутизаторы, коммутаторы (L2/L3) | core/distribution switches | DDoS на управление, отказ питания, переполнение таблиц | — |
| Межсетевые экраны, СЗИ | firewall, VPN-шлюз | DDoS, обход защиты, компрометация конфигурации | — |
| Узлы спутниковой связи | VSAT-станции (каналы F1, F7 по табл. 3.1 презентации) | РЭП, погодные воздействия, отказ оборудования | — |
| Береговые и маячные объекты | радионавигационные станции, NAVTEX | физическое воздействие, разрыв канала электропитания | — |

### 2.3. Узлы хранения и передачи данных

| Тип узла | Примеры | Воздействия |
|----------|---------|--------------|
| Системы хранения (СХД) | SAN/NAS-массивы, распределённый реестр (кластер ЦМ БД) | отказ дисковой группы, целенаправленное искажение записей, «отравление» данных |
| Каналы связи как узел | выделенный канал ЕСИМО, VPN-канал АС ГМО, линия E1 | разрыв/подавление (РЭП), DDoS, физическая порча линии |
| Почтовые/транспортные серверы | серверы доведения НАВИП/ПРИП | перегрузка, компрометация учётных данных |

## 3. Узлы, которые нельзя рассчитать напрямую

| Ситуация | Почему не подходит | Что делать |
|----------|--------------------|------------|
| Многосостоянный узел (работает / деградировал / отказал) | модель двухсостоятельна | разбить на несколько двухсостоятельных узлов или ввести эквивалентную интенсивность отказов «критического состояния» |
| Узел с немарковским восстановлением (детерминированное время ремонта, запчасти с логистикой) | экспоненциальная модель $\mu$ не описывает | аппроксимация: $\mu = 1/\bar{t}_{\text{восст}}$; точнее — имитационное моделирование |
| Узел, зависящий от состояния других узлов (распределённая СУБД, кворум консенсуса PBFT/Raft, сегмент сети, критичный для связности) | одиночный расчёт не видит топологию | задача 2 реализована: соберите систему через ключ `system` (узлы + связи + `target` + `w_def`), программа оценит $Q(S)$ и важность каждого узла; см. [user-guide.md](user-guide.md) и примеры 6–9 |
| Атаки с меняющейся во времени интенсивностью (кампания, эскалация) | $\lambda_j$ постоянны | кусочно-постоянная $\lambda_j(t)$: считать расчёт на интервалах постоянства |
| Коррелированные воздействия (одна атака бьёт по нескольким узлам) | независимость потоков | консервативная оценка: суммарная интенсивность общих воздействий |
| Узел как «точка отказа» без восстановления в принципе (например, однократный захват с необратимой подменой данных) | при $\mu = 0$ и $T \to \infty$ живучесть → 0, модель вырождается | оценивать вероятность *первого* поражения за $T$: $1 - e^{-\Lambda_i T}$ |

## 4. Как свести сложный узел к модели

Для узла с внутренней структурой (сервер с RAID, кластер из $N$ машин,
маршрутизатор с резервированным БП):

1. **Эквивалентная интенсивность собственных отказов.** Если отказ узла
   наступает при отказе $k$ из $N$ одинаковых компонентов, интенсивность
   $\lambda_i^{(0)}$ берётся для события «узел неработоспособен», а не для
   отдельного компонента (например, для последовательной схемы
   $\Lambda \approx \sum \lambda_k$).
2. **Эквивалентная вероятность поражения.** $p_{ij}$ — вероятность того, что
   воздействие $d_j$ выводит из строя именно узел целиком (с учётом его
   защищённости и резервирования).
3. **Эквивалентное восстановление.** $\mu = 1/\bar{t}_{\text{восст}}$, где
   $\bar{t}_{\text{восст}}$ — среднее время восстановления *узла* (включая
   переключение на резерв при горячем резервировании).
4. **Проверка по предельным случаям.** После агрегирования полезно прогнать
   расчёт при $\Lambda_i \to 0$ (ожидается $Q_i \to 1$) и при $\mu = 0$
   (ожидается $Q_i = e^{-\Lambda_i T}$).

## 5. Быстрый выбор параметров по типу узла

| Параметр | Откуда брать значение |
|----------|------------------------|
| $\lambda_i^{(0)}$ | статистика отказов оборудования (наработка на отказ), отчёты службы эксплуатации |
| $\lambda_j$ | частота событий угрозы за период (данные SOC/ЦМУ, оценки по слайдам 2, 4 презентации: DDoS-атаки, кибератаки) |
| $p_{ij}$ | экспертная оценка / результаты тестирований на проникновение с учётом защищённости узла |
| $\mu$ | $1/\bar{t}_{\text{восст}}$ — регламентные времена восстановления, SLA |
| $T$ | период, за который требуется гарантия работоспособности (сутки, неделя, дежурство) |
