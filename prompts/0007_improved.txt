# Задание: выбор рационального способа защиты $g^*$ по показателям живучести

## Контекст

Проект — консольное приложение `survivability` (Python 3.11+, только
стандартная библиотека) в `F:\dev\elsur`. Реализованы:

- **задача 1** — живучесть узла $Q_i = P(x_i(T)=1)$ (модуль
  `survivability/calc.py`, формулы (1)–(11) в `doc/formulas.tex`);
- **задача 2** — живучесть системы $Q(S) = P\!\left(W(X) \geq
  W_{\text{доп}}\right)$ (`survivability/system_calc.py` по заданию
  `prompts/0006.txt`: точный перебор при $n \leq 20$, Монте-Карло с
  доверительным интервалом Уилсона при $n > 20$, варианты $W$:
  `node_fraction`, `connectivity`, важность узлов).

Теперь требуется реализовать **третий блок формальной постановки**
(`materials/Слайд Бойко26.09.  Исп.pptx`, слайд 8 «Выбор способа
защиты», и ЧНЗ №4 на слайде 9):

$$g^* = \arg\max_{g \in G} Q_g(S) \quad \text{при} \quad C(g) \leq C_{\text{доп}},$$

где $G$ — множество альтернативных вариантов защиты, $Q_g(S)$ — живучесть
системы с защитой $g$ (оценивается прогонами на цифровом двойнике, как и
$Q(S)$), $C(g)$ — затраты на вариант, $C_{\text{доп}}$ — бюджет.

Научный смысл задачи (слайд 7): оценки на единичных сценариях невоспроизводимы
и несопоставимы — поэтому сравнение вариантов обязано быть **статистически
корректным** (см. требование 2 про воспроизводимость Монте-Карло).

Текущие ограничения зафиксированы в `doc/report.md` (разделы 4–5) — после
реализации их нужно актуализировать.

## Требования

### 1. Модель вариантов защиты

Расширь формат входного JSON (ключ верхнего уровня `protection` рядом с
`system`; отсутствие ключа — обычный расчёт $Q(S)$, обратная совместимость
обязательна):

- `budget` — $C_{\text{доп}} \geq 0$;
- `variants` — список вариантов, каждый:
  - `name` — уникальное имя варианта;
  - `cost` — $C(g) \geq 0$;
  - `nodes` — переопределения параметров узлов (по имени узла, только те
    поля, что меняются): `own_failure_rate` ($\lambda_i^{(0)}$),
    `recovery_rate` ($\mu$), `impacts` — новый список воздействий с
    пониженными $p_{ij}$ (экранирование, фильтрация трафика, обучение);
  - `links_added` — добавляемые резервные связи (пары имён узлов) —
    структурное резервирование для `connectivity`;
- валидация: имена вариантов уникальны, `cost` $\geq 0$, переопределения
  ссылаются на существующие узлы, вероятности $p_{ij} \in [0; 1]$,
  интенсивности $\geq 0$, добавляемые связи — без петель и дубликатов
  существующих, `budget` $\geq 0$, список `variants` непуст (если ключ
  `protection` есть).

Архитектурно: вариант защиты — «накладка» над базовым `SystemInput`,
порождающая новый `SystemInput` с изменёнными параметрами; не дублируй
парсинг, переиспользуй существующую валидацию.

### 2. Расчёт $Q_g(S)$ и выбор $g^*$

Новый модуль `survivability/protection.py`:

- для каждого варианта $g$: пересчитать живучести узлов $Q_i^g(T)$ с
  изменёнными параметрами (переиспользуй `survivability/calc.py`), затем
  $Q_g(S)$ — переиспользуй `system_calc.py` с теми же правилами
  (перебор/Монте-Карло);
- **воспроизводимость Монте-Карло**: зерно ГПСЧ фиксируется полем JSON
  `seed` (по умолчанию константа) и параметром CLI `--seed`; для всех
  вариантов используется **общий поток случайных чисел** (один генератор,
  последовательные прогоны) — это снижает дисперсию сравнения и делает
  оценки $\hat{Q}_g(S)$ зависимыми от одних случайностей, а не от разных
  потоков;
- допустимое множество: $G_{\text{доп}} = \{g : C(g) \leq C_{\text{доп}}\}$;
  если оно пусто — понятная ошибка с перечнем $C(g)$ и $C_{\text{доп}}$,
  код возврата 2 (как у прочих ошибок ввода);
- $g^* = \arg\max_{g \in G_{\text{доп}}} \hat{Q}_g(S)$; при равенстве —
  меньшая стоимость, затем имя (детерминированная устойчивость);
- производные показатели для обоснования решения: прирост живучести
  $\Delta Q = Q_{g^*}(S) - Q_{\text{base}}(S)$ (базовая система без защиты
  считается всегда, даже если не входит в `variants`), относительный прирост
  $\Delta Q / Q_{\text{base}}$, эффективность затрат $\Delta Q / C(g^*)$;
  при Монте-Карло разность оценивать на общих прогонах и сопровождать
  шириной интервала.

### 3. CLI и вывод

- `python -m survivability --file system.json` распознаёт `protection`:
  есть ключ — режим сравнения вариантов, нет — прежний расчёт $Q(S)$;
- консольный отчёт: сводная таблица (вариант, $C(g)$, допустимость,
  способ расчёта, $Q_g(S)$, ДИ для Монте-Карло, $\Delta Q$ к базе),
  выделенная строка $g^*$, блок производных показателей;
- экспорт `--output`: CSV — таблица сравнения; JSON — то же плюс `chosen`,
  `budget`, `seed`, базовое $Q_{\text{base}}(S)$ и его ДИ.

### 4. Тесты

Добавь в `tests/` (unittest, стиль как в `tests/test_calc.py`):

- аналитика на двухузловой системе: вариант, снижающий $p_{ij}$ узла,
  монотонно повышает $Q_i^g$, и $Q_g(S)$ совпадает с эталоном перебора;
- структурное резервирование: линейная цепочка 1–2–3 с `connectivity`,
  $W_{\text{доп}} = 1$; вариант с добавленной связью 1–3 даёт
  $Q_g(S) = 1 - (1-Q_1)(1-Q_2)(1-Q_3)$ — сверить с расчётом;
- бюджет: лучший по $Q$, но дорогой вариант отбрасывается; пустое
  допустимое множество — ошибка с текстом;
- детерминизм: два запуска с одним `seed` дают побитово одинаковые
  оценки и одинаковый $g^*$;
- валидация: дубликат имён вариантов, `cost` < 0, переопределение
  несуществующего узла, $p_{ij} > 1$, петля в `links_added`;
- обратная совместимость: все `examples/example*.json` без `protection`
  работают без изменений.
